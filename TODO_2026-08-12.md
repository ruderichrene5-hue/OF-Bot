### 3.2 It classified as the SMS code screen — fixed

The wording is **"enter the code from the image"**, which contains
`_CODE_STRONG_MARKERS`' `"enter the code"`. None of the old
`_IMAGE_CAPTCHA_MARKERS` ("type the characters you see", etc.) appear on this
screen at all, so it fell through to `CHALLENGE_CODE`.

With `--apply` that would have called `_handle_code`, which waits **45 seconds
for an SMS on a chain where no number had been rented**, then declares the code
never arrived. Expensive and completely undiagnosable from the outside.

Fixed by adding the real markers, which are checked before the code markers:
`confirm you're human`, `code from the image`, `can't read this text`,
`hear this code`. The screen is pinned verbatim as a test fixture, with a test
asserting it is *not* the code screen.

**The general lesson, worth more than the fix:** a screen classified as the
*wrong* challenge is worse than one classified as `none`. `none` at least stops
the run (and is now doubted — §4.5); a wrong label makes the loop confidently
do the wrong thing. Every new marker list should be checked in both directions.

### 3.3 The image renders late, and sometimes not at all — handled

First probe: the image node was present, correctly sized, and **pure white on
all 8 looks across 90 seconds** (std 0.00, one unique colour).

Second probe: **blank at t=0, readable by t=15s** — same node, same bounds,
std 113.66.

So blank usually means *not yet*, not *never*. Two changes:

- `capture_captcha_image` now re-screencaps up to 4 times, 5s apart, while the
  crop is blank. A broken screencap is **not** retried — it will not fix
  itself, and blank is the only condition worth waiting on.
- `image_is_blank()` (stddev < 3.0) refuses to hand a flat crop to a paid
  solver. It returns **None**, not False, when cv2 is missing or the file will
  not open: not knowing must not cost money either way.
- If it is still blank, the flow taps the screen's own `Get a new code`
  (`request_new_captcha`, its own label list — deliberately *not* shared with
  `_NEW_NUMBER_LABELS`, or a captcha failure could tap a change-number link and
  abandon a number about to receive) and re-enters the loop, up to
  `MAX_CAPTCHA_IMAGES = 2`, then `needs_human`.

      profiles, takes the `ProfileLocks` the posting and warm-up loops respect,
      launches, runs `run_verification`, writes the result back, shuts the

          python -m adb_bot.automation.verification_runner --limit 5
          python -m adb_bot.automation.verification_runner --limit 5 --apply

- [x] **4.2 Route on the result, not on the tag.** `route_result()`, tested on
      its own because it is where a mistake hands a broken account back to the
      posting loop.
      - `solved` → untag `Issue` in MultiLogin, **and nothing else**. That one
        write is the whole hand-back: `issue_tags` clears `Needs Human Check`,
        then `recovery_runner` sets Status Active and re-queues. Writing any of
        that here too is what stranded profiles last time.
      - `banned` → flag the profile `Banned / Blocked`, keep the tag on.
      - `signed_out` → change nothing.
      - `needs_human` / `stuck` / `failed` → change nothing.
- [x] **4.3 Do not let a cleared profile re-flag itself** — *half done.* The
      runner keeps an attempt ledger (`~/.adb_bot/verification_attempts.json`)
      and will not reconsider a profile for `DEFAULT_COOLOFF_HOURS` (6),
      whatever the result. **This bounds the runner's spending, not the posting
      loop's eagerness.** A cleared profile still becomes postable the moment
      `recovery_runner` reactivates it; a delay there belongs in the posting
      planner and is still open.
- [ ] **4.4 Breaker state on the dashboard.** `cli.py state` already prints
      active provider, failure count and cooldowns. Those three answer "why is
      verification suddenly using 5sim?" without an SSH session.
- [x] **4.5 One read is not enough.** Done, and it turned out to be a live bug
      rather than a precaution: `run` read the screen once, and a clear screen
      classifies as `none`, which it returned as **`solved`**. So a flagged
      account whose challenge had not drawn yet was reported solved without
      ever being looked at. `_confirm_clear` now waits 15s re-reading, then
      pulls the feed down and looks again, before believing a clear screen.

- [ ] **4.6 A timer.** Still the last step, and now the only one. The
      hardening in §4b is what a timer needed; what remains is the decision
      about burn rate, which is money rather than code.

      The pass costs up to 3 numbers × `--limit` profiles per tick and is
      bounded at `MAX_RUN_SECONDS` (15 min) per account, so `--limit 3` is at
      most ~45 minutes and ~$5.40 worst case. At SMSPool's $7.95 that is
      **one tick and a bit** before the wallet is the thing stopping you — so
      top up first, or start at `--limit 2` a couple of times a day.

      It exits non-zero on a fleet-level abort, so the unit can alert on that
      without a log parser.

## 4b. Hardening for unattended running

The two halves work. This is what stood between "works when watched" and "runs
on a timer", found by replaying every screen ever recorded
(`~/.adb_bot/verification`, ~114 of them) through the classifier.

### 4b.1 `solved` was a claim made on no evidence — fixed

`run` returned **SOLVED** for any screen carrying no challenge marker. Replaying
the recordings, that is not one screen but four:

| screen | what it really is | old verdict |
|---|---|---|
| healthy feed | fine | solved ✓ |
| **Android launcher** | Instagram never started; `Jil 2` sat here 2 min | solved ✗ |
| **Meta ads-consent gate** | blocks the app until answered (`Jil 20`) | solved ✗ |
| **empty read** | the dump returned nothing at all | solved ✗ |

Three of four would have untagged a profile nobody fixed and handed it back to
posting. Since §4.2 routes `solved` → untag, this was the single most dangerous
thing in the flow.

Now `screen_is_healthy()` is a **whitelist** built from real dumps — the nav
bar (`search and explore`, `home reels message`), the story tray (`add to
story`, `reels tray container`), and `you're back on instagram` /
`no longer suspended`, which is what a cleared chain actually ends on and is
*not* a feed. Anything else → `needs_human`, with the screen text in the
detail so the marker lists can grow.

**Why a whitelist:** a blacklist of "screens that are not the feed" cannot be
written, because the problem is the screens nobody has seen yet. Erring this
way costs a glance at a profile that already carried the tag. Erring the other
way costs days of launches on a phone that cannot post.

Current split across all recorded screens: 20 healthy → solved, 3 consent gate
→ person, 6 unrecognised → person, and the rest classified as real challenges.

### 4b.2 The other three

- **A captcha we answered is no longer "the last one"** once a different screen
  appears. Instagram does re-ask; without the reset a later captcha reported
  the *earlier, correct* answer to 2captcha as wrong — refunding a solve we
  should have paid for and feeding the service bad accuracy data.
- **A wall-clock budget per account** (`MAX_RUN_SECONDS = 900`). `MAX_STEPS`
  bounded screens, not minutes, and 3 numbers × 45s + captcha waits + clear
  screen doubt add up. Checked *before* a step starts, so the run never rents a
  number it has no time to use, and every held number is still settled on exit.
- **The pass stops after 2 fleet-level failures in a row** — empty wallet,
  provider refusing, MultiLogin not starting phones. All give the same answer
  for every phone, and each costs a launch and ~4 minutes to re-learn. Exits
  **non-zero** so a timer can tell that apart from ordinary work.

### 4b.3 An Android permission dialog is not a failed launch

`632451306307322212`, 2026-08-12 17:36: Instagram was running fine, but
`com.android.permissioncontroller/.GrantPermissionsActivity` held the
foreground for the entire 75s launch window. The probe refused to read the
screen and exited 5 — correct, since whatever is on that screen says nothing
about the account — but nothing was ever going to dismiss the dialog, so the
profile was simply unreachable. The 75 seconds of identical log lines were the
loop re-issuing a start intent, which does exactly nothing in that state.

Now gated on the **foreground package** rather than text markers (the package
is definitive; a dialog whose wording nobody has seen still reports as
`permissioncontroller`, and this fleet is not one Android build), and granted
through `interruptions._advance_permission_screen` — the same code the posting
and warm-up flows already use, so there is one answer to this question and not
two. Its label match is EXACT, so `Allow` can never hit `Don't allow`.

Clearing one buys 30s more launch time, up to 6 dialogs: a fresh profile can
face a chain, and timing out halfway through would report a phone that was
actively being fixed as one that never started. Bounded, so a dialog that
reappears for ever still ends the run.

**Intermittent** — the same profile launched cleanly ten minutes later. Tested
against fakes; the real dialog has not been hit again since the fix.

Useful side-observation from that clean launch: the foreground activity was
`com.instagram.challenge.activity.ChallengeActivity`. That is a positive signal
that an account is mid-challenge, available before any screen is read.

### 4b.4 The consent gate is deliberately not automated

Its only control is `Get started`, and behind it is a *consent choice* about
processing personal data for ads. What an account consents to on its owner's
behalf is not the bot's decision. It is **named** so a VA is told which screen
to clear rather than handed a paragraph of raw text. If it turns out to be
common, the decision to make is "which option do we pick, and who says so" —
not "how do we tap it".

## 7. Things worth knowing before you touch it

- **A screen classified as the *wrong* challenge is worse than one classified
  as `none`.** `none` stops the run and is now doubted twice before it is
  believed; a wrong label makes the loop confidently do the wrong thing. The
  captcha read as the SMS code screen and would have waited 45s for a text on a
  chain with no number in it. Check every new marker list in both directions.
- **Images on these screens render *after* the screen around them.** Blank at
  t=0 does not mean broken; it means look again in five seconds. True of the
  captcha image, and worth assuming for anything else visual.
- **"No challenge on screen" is not the same as "solved".** That mistake was
  live in this code until a real phone showed it. Anything added to
  `classify_challenge` should be checked against the same question: if the loop
  cannot see a challenge, is returning SOLVED actually true?
- **Exact-match button rules fail silently on longer labels.** `send` does not
  match `Send code`; `resend code` is not `Update mobile number`. Both were
  wrong until a real dump showed the full text. Check the whole label, not the
  verb.
- **Profile names are not unique**, and a profile's state is not stable —
  `Jil 23` went from healthy feed to phone challenge in twenty minutes.
- **The failure counter is on disk on purpose.** Each loop is a separate systemd
  run; an in-memory counter would reset every time and a pool failing twice per
  run would never reach ten.
- **A diagnostic must not be able to bench a provider.** `cli.py rent` cannot
  receive a code by construction, so its timeout is a successful test, not a
  failure. It now writes to a scratch breaker file; `--count-failures` opts back
  in.
- **`monkey` starts nothing on these phones** — it returns an empty string and
  leaves the launcher up, while `am start` works. The production flows are
  *not* affected: all 8 of their launch builders issue both. Checked 2026-08-11.
- **A phone can report ADB-ready and still be `offline`**, and cold launches take
  50–65s against a shipped default of 20s.
