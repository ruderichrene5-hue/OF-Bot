# Status & next steps — updated 2026-08-12, verification flow against real phones

**Everything that reads a challenge screen is now evidenced on live phones.
Everything that writes to one is still untested.** The flow can find a flagged
profile, launch it, recognise which step of Instagram's chain it is on, rent a
German number and give it back. What has never happened is the middle: typing a
rented number into a real challenge screen and submitting the code it receives.
That is one command, and it is the only thing standing between this and a
working feature.

Yesterday's file (`TODO_2026-08-11.md`) has the full archaeology of how the
driver's selectors were found and corrected. This one is what to do next.

## 4. Wire it in

Only start once §2.1 has worked on one profile by hand.

- [ ] **4.1 A runner.** Picks flagged profiles, takes the profile lock, launches,
      runs `run_verification`, writes the result back. `recovery_runner.py` is
      the closest existing shape. Results are `solved` / `needs_human` /
      `banned` / `stuck` / `failed` / `signed_out`.
- [ ] **4.2 Route on the result, not on the tag.**
      - `solved` → untag `Issue` in MultiLogin (`automation/issue_tags.py`)
      - `banned` → ban state via `incidents.py`; do not untag
      - **`signed_out` → change nothing.** The account needs credentials, not
        verification. Untagging it would hand a logged-out profile back to the
        posting loop. This is not hypothetical — `Jil 2` is exactly this, and
        before `signed_out` existed the loop reported it as **solved**.
- [ ] **4.3 Do not let a cleared profile re-flag itself.** A profile cleared here
      is eligible to post within minutes. If the account is still shaky it gets
      re-flagged immediately and the run has spent real money for nothing.
      Consider a cool-off before a cleared profile is eligible again.
- [ ] **4.4 Breaker state on the dashboard.** `cli.py state` already prints
      active provider, failure count and cooldowns. Those three numbers answer
      "why is verification suddenly using 5sim?" without an SSH session.
- [ ] **4.5 One read is not enough.** `Blank (24)`'s first look was an ordinary
      feed; the "we disabled your account" screen only appeared on the second, a
      few seconds later. `run_verification` is safe because it re-reads every
      pass, but any health check built on a single read will call a banned
      account fine.

## 5. Decisions still open

- [ ] **5.1 Which picture the photo challenge uploads.** `upload_photo()` has to
      upload *a picture of a person* and nothing in this repo owns one. The
      model's media folder is the obvious source (`get_folder_media_path`), but
      whether a reel frame passes Instagram's check is unknown, and the wrong
      face on the wrong account is a real harm that failing the step is not.
      This may correctly end as "the photo challenge stays a `needs_human`".
- [ ] **5.2 Whether 10 consecutive failures is still the right trip point.** The
      threshold was chosen against US-pool odds (71% success). Germany quotes
      **56%** at SMSPool, so roughly one attempt in two fails legitimately and
      the breaker will trip more often. If it starts switching providers over
      normal German-pool behaviour, change the constant — not the country. The
      country is fixed by the form (`DE +49`) and the phones.
- [ ] **5.3 When to merge.** The branch only adds modules; merging changes no
      existing behaviour. Nothing schedules the flow, so merging early is cheap
      and keeps it off a stale base.

## 7. Things worth knowing before you touch it

- **"No challenge on screen" is not the same as "solved".** That mistake was
  live in this code until a real phone showed it. Anything added to
  `classify_challenge` should be checked against the same question: if the loop
  cannot see a challenge, is returning SOLVED actually true?
- **Exact-match button rules fail silently on longer labels.** `send` does not
  match `Send code`; `resend code` is not `Update mobile number`. Both were
  wrong until a real dump showed the full text. Check the whole label, not the
  verb.
- **Profile names are not unique**, and a profile's state is not stable —
  `Jil 23` went from healthy feed to phone challenge in twenty minutes.
- **The failure counter is on disk on purpose.** Each loop is a separate systemd
  run; an in-memory counter would reset every time and a pool failing twice per
  run would never reach ten.
- **A diagnostic must not be able to bench a provider.** `cli.py rent` cannot
  receive a code by construction, so its timeout is a successful test, not a
  failure. It now writes to a scratch breaker file; `--count-failures` opts back
  in.
- **`monkey` starts nothing on these phones** — it returns an empty string and
  leaves the launcher up, while `am start` works. The production flows are
  *not* affected: all 8 of their launch builders issue both. Checked 2026-08-11.
- **A phone can report ADB-ready and still be `offline`**, and cold launches take
  50–65s against a shipped default of 20s.

## 8. Not this branch, but happening around it

A parallel session raised the posting retry limit 3→5 (`5d51568`, already in
this branch's base) and is waiting for a gap between posting runs to deploy it.
When it fires, all 15 `adbbot-*.timer` units pause and `adbbot-site` /
`adbbot-report` restart — under a minute. Timers briefly inactive or :8088
blipping is that, not a fault.

Its cost on the flagged population is smaller than it first looks: of the 29
profiles tagged both `Issue` and `Active / Posting`, 22 are dropped by the
planner's `needs_human` guard and the other 7 by `Status = Inactive`, so none of
them take attempts at all today. Worth knowing that the planner keys on
Airtable's **`Needs Human Check` checkbox**, not the MLX `Issue` tag — they are
separate flags maintained separately, and those 7 rest only on the hand-owned
park switch.
