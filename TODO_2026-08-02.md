### Output layout (changed 2026-08-02)

```
/opt/adbbot/spoofed/<Model>/run<N>/<source>__<handle>.mp4
```

One run folder per raw video, shared by every active account under the model. Numbering
is per model and continues across invocations (`next_run_dir`). Filenames are sanitised —
the pushed path ends up inside Android shell commands, which split on spaces.

> **Why the rename matters:** `vtf` names output after the SOURCE and is run with
> `--overwrite`. Without renaming each file to `<source>__<handle>` immediately, the
> second account's encode overwrites the first, `build_cli_spoofer` finds no new file,
> falls back to "newest video in the directory", and every account ends up sharing one
> video — silently, reporting `errors=0`. A rename failure is recorded as an error rather
> than written to Airtable.

## 4. Open issues

### Silent failure reporting — highest priority

A flow whose ADB commands all fail still reports success. Proven 2026-08-01: a run had
**163 `device not found` errors**, never ran the follow step, and still logged
`Workflow completed` → `Done: warm_up_process` in Airtable.

Cause: `ADBClient.run_command` catches `CalledProcessError`, prints `[-] ADB command failed`,
returns `None` (`clients/adb.py:51-53`). Flow steps ignore the return value, and every swipe
is logged as `Executed swipe: ...` regardless — the log prints the *command*, not the result.

The heartbeat bounds this (aborts within 60 s when the phone vanishes) but does not fix it:
a live phone whose commands fail for another reason still reports Done. Proper fix: make
command failures count toward a flow-level failure.

Note the reel flow does **not** have this weakness — it verifies via post count. The warm-up
flow has no equivalent check.

### Loop summaries overstate success

`posting result: {'processed': 1, ...}` with exit 0 is printed even when the run failed;
the per-run Airtable write-back is the reliable signal, not the summary line or exit code.
Matters for systemd, which only sees the exit code.

### Others

- **Bio / Profile Picture empty** on accounts → those warm-up flows always pre-skip.
- **Reels gated off** in the warm-up planner (`airtable_planner.py:72` `run_reels=False`;
  the UI never passes it). Separate from posting, which uses its own flow.
- **Warm-up logs "day 1"** regardless of actual day; Rodrigo at day 3 was scheduled only
  `warm_up_process`, no picture/bio.
- **Auto-reconnect ungated** (`flows/instagram.py:256`) by explicit decision — can re-attach
  before the next heartbeat check. ~60 s window.
- **Service accounts have no Drive storage quota** — they can move/rename/read files but
  cannot upload or copy into a My Drive folder. Irrelevant to the bot (it only reads), but
  it blocks scripted test-file creation in Drive.

## 5. Start-of-day checklist

Nothing here survives a reboot.

```bash
# 1. MLX agent (needs the X session; nothing device-related works without it)
cd /opt/mlx && DISPLAY=:10.0 nohup /opt/mlx/agent.bin > /tmp/mlx_agent.log 2>&1 &
sleep 15 && ss -tlnp | grep 45001        # expect a LISTEN line

# 2. Preflight
cd /root/adb_bot
set -a; . /etc/adbbot/env; set +a          # ALWAYS -- creds live here, not in a settings file
.venv/bin/python -m adb_bot.automation.run_loop doctor
```

**If launches return HTTP 500** ("failed to launch mobile profiles"): the agent auto-updates
its launcher, which expects `phone_launcher_linux_amd64` while the installed binary is
`phone_launcher_linux_amd64_webkit2_41`. The real error appears only in
`/root/mlx/logs/launcher_<date>.log`, never in the API response.

```bash
ln -sfn /root/mlx/deps/phone_launcher/phone_launcher_linux_amd64_webkit2_41 \
        /root/mlx/deps/phone_launcher/phone_launcher_linux_amd64
```

## 6. Running the flow

```bash
cd /root/adb_bot
set -a; . /etc/adbbot/env; set +a

.venv/bin/python -m adb_bot.automation.run_loop pipeline

# Post: needs a Posting Queue row (see below)
.venv/bin/python -m adb_bot.automation.run_loop posting
.venv/bin/python -m adb_bot.automation.run_loop posting --apply

# Warm-up
.venv/bin/python -m adb_bot.automation.run_loop warmup --apply
```

### Posting Queue row fields

| Field | Value |
|---|---|
| `Target Account` | link → Rodrigo (test) `recbvoZla049GNiGa` |
| `Spoof Variant` | link → a Spoof Variants row |
| `Caption` | link → Caption Pool row (optional — planner allows none) |
| `Scheduled DateTime` | must be **in the past** or it isn't due |
| `Post Status` | `Pending` |

A `Failed` row is **not** retried automatically (`list_pending_posts` filters on `Pending`).
Set it back to `Pending` to retry; `Retry Count` has no maximum and never blocks a run.

### Idempotency — why a re-run may do nothing

- **Warm-up**: `todays_completed_runs` counts Run Log rows `Done` **or** `Running` today. A
  SIGKILLed run leaves a stale `Running` that suppresses planning — clear it manually.
- **Pipeline**: skips any raw filename already in Content Pipeline. To re-test, use a new
  filename or delete the Content Pipeline row.

Force a warm-up past the guard (`override_flow` short-circuits the lifecycle planner):

```bash
PYTHONPATH=/root/adb_bot .venv/bin/python /root/force_warmup.py
```

Pins `selected_launch_ids` to Rodrigo so it cannot touch another profile.
