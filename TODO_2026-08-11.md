# Status & next steps — updated 2026-08-11 (evening), SMS verification build

**The whole chain is now written, including the device half. What is missing is
a confirmed sighting of a real challenge screen.** A profile flagged `Human
Verification Required` can be walked through Instagram's captcha → phone → code
→ photo chain in any order, with numbers rented from SMSPool and 5sim behind a
circuit breaker, driven by a real ADB driver that records every screen it sees.
Nothing schedules it, and **the marker phrases it matches on have still never
been checked against a screen this fleet actually shows** — that is the one
thing standing between this and a working feature.

Design write-up: `SMS_VERIFICATION.md`. Branch `worktree-sms-verification`,
based on `integration` (not `main`). PR not opened — `gh` is unauthenticated
here, so use the link `git push` printed.

### How to look at a flagged profile

    python -m adb_bot.automation.verification_probe --list
    python -m adb_bot.automation.verification_probe --profile "Jil 2"
    python -m adb_bot.automation.verification_probe --sweep 10

Without `--apply` that launches the phone, opens Instagram, and reads the screen
on a timer without touching it — saving the UI dump, a screenshot and the
extracted text to `~/.adb_bot/verification/<name>-<stamp>/`. It rents nothing
and taps nothing, so it is safe on a live account. `--apply` runs the real
thing and spends money.

`--sweep N` walks N flagged profiles in turn, verification-remarked ones first.
That is the one to reach for: **most flagged profiles are not showing a
challenge**, so finding a real one is a search, not a single run. A sweep is
always observation only. Budget ~2 minutes per profile, nearly all of it
waiting for MultiLogin to start the phone.

### What three runs against Jil 2 established

`Jil 2` (`624743063687856180`, tagged `Active / Posting` + `Issue`) was the test
subject. Recordings are in `~/.adb_bot/verification/Jil-2-2026081*/`.

**The headline: `Jil 2` is not showing a verification challenge at all — it is
signed out of Instagram.** The screen is the welcome page ("Join Instagram /
I already have a profile"), and the foreground activity says so before any text
is read: `com.instagram.nux.activity.BloksSignedOutFragmentActivity`.

That found a real bug, now fixed. A signed-out screen carries no challenge
marker, so the loop read it as "nothing left to answer" and returned **SOLVED**.
Wired to the runner in section 4, that would have cleared the `Issue` tag on
every logged-out profile and handed dead accounts back to the posting loop.
There is now a `CHALLENGE_SIGNED_OUT` / `RESULT_SIGNED_OUT` pair, its markers
taken verbatim from this dump, and `SignedOutTest` pins it.

**Expect a lot of these.** The `Issue` tag is applied by hand and covers several
different problems; the remarks on tagged profiles include `log in again`,
`disable` and `no ig account` alongside `human verification`. Any runner built
in section 4 has to route on the *result*, not just on the tag.

Three fleet facts, each of which cost a run to find:

1. **Launch is slow.** ~50–65s (3–4 readiness attempts) to become ADB-ready,
   against a shipped default of 20s. Hence the probe's
   `--readiness-attempts 8 --readiness-wait 15` defaults.
2. **`monkey` silently starts nothing on these phones.** It returned an empty
   string and left the Android home screen up, three runs running;
   `am start -n com.instagram.android/.activity.MainTabActivity` worked
   immediately. The probe now uses `am start` first and keeps `monkey` as the
   fallback. **Worth checking whether the posting and warm-up flows are hitting
   the same thing** — they try `monkey` first.
3. **A phone can report ready and still be offline.** One run passed
   MultiLogin's readiness check, got an ip/port, then sat in
   `error: device offline` for the whole connect budget. There were 107 stale
   `offline` entries in the local adb server; `adb disconnect` clears them but
   the running loops re-create them constantly.

## 2. Do these first — they are cheap and they unblock the rest

- [ ] **2.1 Run one live rent.** `python -m adb_bot.clients.sms.cli rent`
      (~$0.42, refunded on cancel). This is the only unverified path in the SMS
      layer: it exercises SMSPool's `/purchase/sms` → `/sms/check` → `/sms/cancel`
      for real. It was blocked by a permission classifier during the build, so
      the response shapes are handled defensively rather than confirmed.
      Watch for: the field names in the purchase response (`number` / `cc` /
      `phonenumber` / `order_id`), and whether the number comes back split or
      as one international string.
- [ ] **2.2 Write down the `/sms/check` status numbers you see.** Only `6`
      (refunded) is publicly documented. `_DEAD_STATUSES` in
      `clients/sms/smspool.py` is the single place to correct. The code decides
      on the presence of SMS text first and treats any unknown status as "still
      pending", so a wrong guess costs the remainder of the 45s — it cannot make
      the poller give up on a code that was about to land.
- [ ] **2.3 Top the accounts up before any real batch.** At ~$0.42 per US
      Instagram number, SMSPool's $9.17 is about 20 attempts. A flagged profile
      is allowed 3 numbers, so that is ~7 accounts before the wallet is the
      thing that stops you — and an empty wallet deliberately does *not* trip
      the breaker, because switching providers cannot fix it.
- [ ] **2.4 Decide the number pool.** Today it is SMSPool country `1` (real US)
      and 5sim `usa` / operator `any`. SMSPool also sells country `22` (US
      Virtual), cheaper but rejected by Instagram more often. `cli.py` has no
      flag for this yet; it is two dicts at the top of each provider module.

## 3. Confirming the driver against real screens — the actual work

The driver is written (`flows/verification_driver.py`, tested in
`tests/test_verification_driver.py`). What is *not* done is the part only a
phone can tell you: whether the words it matches on, and the controls it taps,
are the ones these accounts actually show.

- [ ] **3.1 Catch one real challenge screen.** `--sweep N` is the tool; `--list`
      gives 68 candidates. Expect to work through a lot of them — two profiles
      looked at so far, and neither was mid-challenge (`Jil 2` signed out,
      `Jil 23` on a healthy feed with a stale `human verification` remark).
      Every look is saved under `~/.adb_bot/verification/`, so a sweep can be
      left running and read afterwards. **Check the `.txt` of any look that
      classified as `none`** — that is where a missing marker hides.
- [ ] **3.2 Correct the marker lists from those dumps.** The phrases in
      `_PHONE_STRONG_MARKERS`, `_CODE_STRONG_MARKERS`, `_PHOTO_MARKERS`,
      `_IMAGE_CAPTCHA_MARKERS` and `_CHOOSE_METHOD_MARKERS` are from general
      knowledge of Instagram's wording, **not** from this fleet's actual
      screens. Any that never appear are dead weight; any screen that classifies
      as `none` is a hole the loop walks straight past. Add a fixture per
      confirmed screen to `tests/test_verification_flow.py` as you go.
- [ ] **3.3 Confirm the driver's own guesses.** Three things in it are
      reasoned, not observed, and each is one edit once a real dump exists:
      `_SUBMIT_LABELS` / `_SMS_OPTION_LABELS` / `_NEW_NUMBER_LABELS` (the exact
      button labels), the field hints in `_PHONE_FIELD_HINTS` and friends (which
      box gets typed into), and `looks_like_captcha()` (which image on screen is
      the captcha). The field picker deliberately **refuses to guess** when a
      screen has several unlabelled boxes, so a wrong hint list shows up as a
      clean "refusing to guess" warning rather than a number typed into the
      wrong field.
- [ ] **3.4 Answer the photo question.** `upload_photo()` returns False on
      purpose — it has to upload *a picture of a person* and nothing in this
      repo owns one. The model's own media folder is the obvious source (see
      `get_folder_media_path`), but whether a reel frame passes Instagram's
      check is unknown, and using the wrong face on the wrong account is worse
      than failing the step. This is a decision, not a coding task, and it may
      end with the photo challenge staying a deliberate `needs_human`.
- [ ] **3.5 Watch `request_new_number()` on a real code screen.** After a
      45-second timeout the loop has to get from the code screen back to the
      phone screen. The driver tries the known link labels and falls back to
      Back; whether that lands on the phone screen or somewhere else is the kind
      of thing only the recording will show.

## 4. Wiring it in

Only start this once 3.3 works on one profile by hand.

- [ ] **4.1 A runner.** `run_verification` returns a `VerificationResult` with a
      status (`solved` / `needs_human` / `banned` / `stuck` / `failed`) and a
      readable detail. Something has to pick flagged profiles, take the profile
      lock, launch, run it, and write the result back. `recovery_runner.py` is
      the closest existing shape to copy.
- [ ] **4.2 Clear the flag on success — and only on success.** The `Issue` tag
      in MultiLogin is the whole interface: tagging flags a profile, untagging
      clears it and reactivates it (`automation/issue_tags.py`). A `solved`
      result should untag; `banned` should go the other way and set the ban
      state via `incidents.py`. **`signed_out` must leave the tag exactly where
      it is** — the account needs credentials, and untagging it would put a
      logged-out profile back into posting. That result exists precisely because
      the flow met one (see section 1), so this is not a hypothetical branch.
- [ ] **4.3 Do not let it re-flag itself.** A profile cleared by this flow will
      be picked up by the posting loop within minutes. If the account is still
      shaky it gets re-flagged immediately, and the run has spent real money to
      achieve nothing. Consider a cool-off before a cleared profile is eligible
      to post.
- [ ] **4.4 Put the breaker on the dashboard.** `cli.py state` already prints
      active provider, failure count and cooldowns. The same three numbers on
      the dashboard answer "why is verification suddenly using 5sim?" without
      an SSH session.

## 5. Things worth knowing before you touch it

- **The 5sim account is already in heavy manual use** — 289 activation orders,
  almost all `usa:instagram`. Orders from 2026-08-11 show `TIMEOUT` and
  `CANCELED` next to `FINISHED` ones, which is the burned-pool problem this
  breaker exists for, visible in production data.
- **The failure counter is on disk on purpose.** Each loop is a separate
  systemd run; an in-memory counter would reset every time and a pool failing
  twice per run would never reach ten. If you refactor this into a long-lived
  service, that reasoning changes — but do not "simplify" it back to a global.
- **5sim auto-refunds a `TIMEOUT` order.** The 45-second cancel lands inside the
  window where 5sim can still refuse an explicit cancel, which is why `cancel()`
  returns False rather than raising. A refused cancel is not lost money.
- **A wrong captcha answer costs an attempt on an already-flagged account**, so
  the solver returns `None` rather than guessing. Do not add Tesseract as a
  stand-in; it is nowhere near good enough on distorted images.
- **The phone screen and the code screen contain each other's words.** If you
  touch `classify_challenge`, keep the strong/weak split — the tests in
  `ClassifyTest` pin the two cases that break first. The signed-out markers use
  the same split for the same reason: "Forgot password?" is plausible under a
  challenge form, so it is a weak marker and never outvotes a real challenge.
- **"No challenge on screen" is not the same as "solved".** That mistake was
  live in this code until a real phone showed it. Anything added to
  `classify_challenge` later should be checked against the same question: if the
  loop cannot see a challenge, is returning SOLVED actually true?
- **Every screen the driver reads is written to `~/.adb_bot/verification/`.**
  Nothing cleans it up. That is deliberate — it is the only record of a screen
  that no longer exists — but it does grow, and screenshots are ~2MB on some
  phones and ~130KB on others.
