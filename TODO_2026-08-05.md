## 3. Build these to make it more automatic

Ordered by what actually cost us the most last night.

### 3.1 A systemd unit for the MLX agent  — *highest value*

The agent died **twice** (once to an OOM that killed its session, once earlier),
and both times nothing reported it. Launches simply failed for ~1 h until a
human read the logs. It is a hand-started process with no supervision.

Wants: `Restart=always`, `After=graphical.target`, the `DISPLAY=:0` /
`XAUTHORITY=/var/run/lightdm/root/:0` environment it currently needs, and
`WantedBy=multi-user.target` so it comes back after a reboot.

### 3.2 Release profile locks on SIGTERM

`systemctl stop adbbot-posting` leaves every held lock behind, and the 45-minute
TTL means the next run does nothing at all until they expire. This cost ~17 min
of dead time last night and looked exactly like a hang. A SIGTERM handler that
calls `ProfileLocks.release_all()` fixes it. Same handler should close any phone
still open — see 3.3.

### 3.3 Make the close guarantee survive a kill

`_guarantee_profile_closed` covers a workflow that returns, raises, or hangs.
It cannot cover the process being **killed** (`systemctl stop`, OOM) — neither
the `finally` nor the watchdog timer runs. Phones then leak exactly as they did
before the fix. Same SIGTERM handler as 3.2.

### 3.4 A cross-loop cap on live phones

`MAX_CONCURRENT_PROFILES` is per loop, so posting (10) and warmup (10) and
recheck (1) can be open at once with nothing coordinating them. A shared counter
in the lock directory would make the cap mean what it says. Lower priority now
that phones are actually reaped, but the cap is still not a real ceiling.

### 3.5 Alerting when a loop stops producing

Every silent failure last night looked identical to "quiet": a dead agent, stale
locks, an empty queue. Something that says "posting has launched 0 profiles in
30 minutes while rows are due" would have caught all three within a tick.
`heartbeat.py` already exists — check whether it can carry this.

### 3.6 Watch the MultiLogin 500 rate

`failed to get profiles start urls` ran at 8–36 % of launches all night. It is
their cloud, not ours, and it self-heals — but it silently burns retry budget,
which is how rows reach `Retries Exhausted`. Worth counting per run and logging
the rate, so a bad night is visible rather than inferred.

### 3.7 Re-check the `nikki 9` phone by hand

Came back `unknown` on 8+ consecutive recheck passes and hit repeated launch
500s — the only profile whose problems look device-specific rather than
account-specific. Every other profile eventually resolved one way or the other.

## 4. Fixed last night (for the record, all with tests)

| Bug | Effect if it had shipped |
|---|---|
| `--slots` parsed a string per character | Slots at 00:00/01:00/03:00, not the ones asked for |
| `recheck` called `_sleep_after_instagram_launch()` bare | Every verification returned `unknown`; rows stuck in `Verifying` forever |
| retry moved a row's timestamp off its slot | queue re-filled the "empty" slot → **double posts**. Caught 6 before any went out |
| raw folders `Corina`/`Mandy` matched no model | 23 of 52 profiles had no content at all |
| phones only closed on success | 172 launches vs 64 shutdowns → OOM killed the box twice |
| flagging re-wrote the same note every 30 min | ~48 duplicate lines per profile per day |

Schema added to **Profiles (Cloning)**: `Needs Human Check`, `Issue Reason`,
`Issue Notes`, `Flagged At` — written by the retry pass, never cleared by it.
Clearing the checkbox is the human's signal that somebody looked.

Also added to Posting Queue Issue Type: `Retries Exhausted`, so a row that has
used all 3 retries stops claiming `Failed - Needs Retry`.

**Note on the counters:** the retry tally now reports those rows under
`needs_human`, not `exhausted`, because `Retries Exhausted` is not a retryable
issue type. Count them from `Issue Reason` on the profile instead.
